Here's the CTE I'd write, in raw `text()` (Core's data-modifying-CTE chaining gets ugly fast and I'd rather the repository read like SQL):

```sql
WITH prior AS (
    SELECT content AS content_before
    FROM report_sections
    WHERE report_id = :report_id AND section_key = :section_key
),
updated AS (
    UPDATE report_sections
    SET content = :new_content,
        version = version + 1,
        updated_at = now(),
        updated_by_user_id = :editor_user_id
    WHERE report_id = :report_id
      AND section_key = :section_key
      AND version = :expected_version           -- ← optimistic predicate
    RETURNING version AS version_after, updated_at
),
audit AS (
    INSERT INTO report_section_edits (
        report_id, section_key,
        version_before, version_after,
        content_before, content_after,
        editor_user_id, source
    )
    SELECT :report_id, :section_key,
           :expected_version, updated.version_after,
           prior.content_before, :new_content,
           :editor_user_id, 'human'
    FROM updated, prior                          -- ← CROSS JOIN: audit inserts iff both exist
    RETURNING id
)
SELECT
    EXISTS (SELECT 1 FROM prior)      AS section_existed,
    (SELECT version_after FROM updated) AS version_after,
    (SELECT updated_at    FROM updated) AS updated_at
```

`new_content` bound via `bindparam("new_content", type_=JSONB)` so asyncpg handles dict↔JSONB cleanly — no manual `json.dumps` and `::jsonb` casts littering the SQL.

### Why the CROSS JOIN trick is the whole game

`FROM updated, prior` is a cartesian product. If `updated` has zero rows (version mismatch) the audit `SELECT` yields zero rows → no audit insert. If `prior` is also empty (section missing) same result. So the audit row exists **iff** the UPDATE succeeded — no partial states, no second statement needed.

### Result interpretation (single row, always returns)

| `section_existed` | `version_after` | Meaning | Service action |
|---|---|---|---|
| `false` | `NULL` | Section row doesn't exist | raise `_section_not_found()` (404) |
| `true` | `NULL` | Section exists, version didn't match | raise `_version_mismatch()` (412) |
| `true` | int | Update + audit committed | construct `Section`, commit, log, return |

### Concurrency check (READ COMMITTED, the asyncpg default)

All three CTEs see the snapshot taken at statement start. If a concurrent writer commits between my snapshot and my UPDATE's row re-read, the UPDATE re-evaluates `WHERE version = :expected_version` against the now-newer row and finds nothing → 0 rows → 412. The `prior.content_before` we'd have captured is irrelevant because the audit insert's CROSS JOIN with `updated` produces nothing. No torn state.

`updated × prior = 0 × 1 = 0`. The audit INSERT has nothing to insert. No audit row. ✓

**UPDATE never happens without audit** (the symmetric inverse):

If `updated` produces a row, it matched `report_id=X AND section_key=Y AND version=:expected`. The `prior` CTE selects on the same `report_id=X AND section_key=Y` (no version filter — strictly weaker). So `updated` having a row **implies** `prior` having a row. The CROSS JOIN can't be `1 × 0`. The audit insert always fires when the UPDATE fires.

So the invariant is bidirectional:

```
audit row written  ⟺  UPDATE succeeded
```

Full truth table:

| `prior` rows | `updated` rows | `audit` rows | Outcome |
|---|---|---|---|
| 0 | 0 | 0 | 404 — section doesn't exist |
| 1 | 0 | 0 | 412 — version mismatch, no audit |
| 1 | 1 | 1 | success — UPDATE + audit committed |
| 0 | 1 | — | **impossible** (UPDATE's WHERE is strictly stronger than prior's) |

No orphan audit rows, no silent writes without history. That's why the CROSS JOIN trick is the right shape for this — the linkage is structural, not something the application has to enforce.

Yes, PostgreSQL guarantees exactly one wins — and the mechanism is worth understanding because it's *why* the optimistic-predicate approach actually works.

The mechanism is **row-level locking + EvalPlanQual re-read at READ COMMITTED** (the default isolation for asyncpg).

### Step-by-step trace

Two writers T1 and T2 fire the CTE at the same instant, both with `expected_version = 3`:

```
T1 ──┬─ snapshot S1
     │
     ├─ prior  CTE: reads row, content = "alpha", version = 3 (no lock)
     │
     ├─ updated CTE: UPDATE...WHERE version=3
     │     ↳ matches the row, takes a TUPLE-level EXCLUSIVE LOCK
     │     ↳ writes content="beta", version=4 (uncommitted)
     │     ↳ lock held until commit
     │
     ├─ audit CTE: inserts row { version_before:3, version_after:4, ... }
     │
     └─ COMMIT  ← lock released, row visible as version=4

T2 ──┬─ snapshot S2 (taken before T1 commits)
     │
     ├─ prior  CTE: reads row, sees content="alpha", version=3 (snapshot)
     │
     ├─ updated CTE: UPDATE...WHERE version=3
     │     ↳ tries to lock the row → BLOCKED by T1's lock
     │     ↳ ⏸ waits ...
     │     ↳ T1 commits, lock released
     │     ↳ PostgreSQL re-reads the row at its LATEST committed version
     │       (this is the EvalPlanQual mechanism — special to UPDATE/DELETE
     │       at READ COMMITTED, not regular snapshot semantics)
     │     ↳ row now version=4, re-evaluates WHERE version=3 → FALSE
     │     ↳ skips the row → 0 rows updated
     │
     ├─ audit CTE: FROM updated, prior → 0 × 1 = 0 rows → no audit insert
     │
     └─ SELECT returns: section_existed=true, version_after=NULL → 412
```

T1 gets `200` + version 4. T2 gets `412`. Exactly one winner. Zero torn state, zero phantom audit row.

### The two things doing the work

1. **The row-level lock on UPDATE** serializes the two writers — they can't both perform the update simultaneously. The loser blocks.
2. **EvalPlanQual re-evaluation** at READ COMMITTED re-checks `WHERE version = :expected_version` against the **post-commit** row state when the lock releases. This is what turns "both passed the snapshot check" into "only one passes the post-T1 check." Without it, optimistic concurrency at READ COMMITTED wouldn't work at all.

### Caveats worth knowing

- **Isolation level matters.** This trace assumes READ COMMITTED (asyncpg + SQLAlchemy default). At REPEATABLE READ / SERIALIZABLE, T2 wouldn't silently get 0 rows — it would raise `serialization_failure` (SQLSTATE 40001) and the whole transaction would have to be retried. The code as written would surface this as a 500, not a 412. If anyone ever changes the session isolation, the error handling needs to be revisited.
- **`prior` is unlocked.** That's deliberate. We don't need to lock for content_before because if we lose the version race, we throw away `prior.content_before` (no audit insert). If we win, our snapshot's `content_before` is by definition the version-3 content, which is correct. Locking `prior` with `FOR UPDATE` would serialize **every** read on the row including failed writes — worse contention, no correctness gain.
- **No lost updates possible.** The classic anti-pattern — read version, check in app code, write — would fail here even with the predicate, because two snapshots could both see version=3 and both UPDATEs would proceed if EvalPlanQual didn't re-evaluate. The reason it works is the predicate is *in the UPDATE itself*, which is exactly what CLAUDE.md mandates.

So: PostgreSQL's combination of tuple locking + EvalPlanQual re-read is what makes the spec's "version check in the UPDATE predicate" rule actually enforceable. The CTE inherits all of that for free.

SELECT ...
FROM report_section_edits
WHERE report_id = :rid
  AND section_key = :key
  AND (ts, id) < (:cursor_ts, :cursor_id)   -- only when cursor present
ORDER BY ts DESC, id DESC

Two edits can absolutely share a `ts`, and it's not just theoretical — it'll happen on this codebase. Two reasons:

### 1. `func.now()` is *transaction-start time*, not statement-time

`ReportSectionEdit.ts` defaults to `func.now()`. PostgreSQL's `now()` / `transaction_timestamp()` returns the **transaction start time** — identical for every row inserted in the same transaction.

That matters because:

- **AI rewrite** (planned, next landing) will emit one edit row per section it rewrites. If it batches even two sections in one transaction, both audit rows get the exact same `ts`.
- **Reverts** could also batch (e.g., "revert sections A and B to v3" as one operation) — same `ts` for both.
- **Any future backfill / import script** that wraps inserts in a transaction → every imported edit shares `ts`. Hours of history collapsed onto one timestamp.

So this isn't "two writers racing at the same microsecond" — it's a hard guarantee whenever multiple edits live in one transaction.

### 2. What breaks with a `ts`-only cursor when ties exist

Say a section's edits are `[T5, T4, T4, T3]` and `limit = 3`. Page 1 returns `[T5, T4_a, T4_b]`. Now you build the cursor:

- **Cursor = `T4`, predicate `ts < T4`** → page 2 skips both T4 rows (including `T4_b` which you already showed and the unread `T4_c`). Wait, in my example I only had two T4s — but if there's a third T4 in the table, you lose it. Generally: you **drop** any rows tied on the boundary `ts`.

- **Cursor = `T4`, predicate `ts <= T4`** → page 2 returns `T4_a` and `T4_b` again. **Duplicates**.

Neither is correct. With single-column cursors there's no fix; the column isn't unique enough to identify a page boundary.

### Tuple cursor solves both

Cursor = `(T4, id_b)`, predicate `(ts, id) < (T4, id_b)`. Page 2 starts at the first row strictly older than the one I last showed, which means:

- Any remaining T4 rows with `id < id_b` come first (no drops, no dupes).
- Then T3 and earlier.

Cost: one extra integer in the cursor payload (~5 chars after base64), a marginally more complex predicate (still index-friendly via row-wise comparison). Bug surface: zero.

### Why bother given how rare ties are?

If this were a hand-edit-only system I'd agree the bug is unobservable in practice and we could ship the simpler form. But the **scope of this repo includes AI rewrite and revert**, both of which can write multiple edits per transaction by design. The ties aren't a low-probability concurrency race — they're the expected behavior of features sitting one PR away.

Cheaper to write the correct cursor now than to ship a pagination bug that only manifests once AI rewrite lands and someone files "history skips the 3 AM batch."

### Dropping If-Match means I need `FOR UPDATE` to keep audit rows accurate

This is the part worth surfacing. Without a version predicate in the UPDATE, the CTE has a subtle race that would corrupt audit rows. Walk-through:

```
T1 snapshot: prior sees version=3, content=X.
T1 UPDATE: no version predicate, just matches the row. Sets to v4, content=Y. Lock held.
T1 audit: content_before=X, content_after=Y. COMMIT.

T2 snapshot taken BEFORE T1 commits: prior sees version=3, content=X.
T2 UPDATE: blocks on T1's lock. T1 commits. EvalPlanQual re-reads — row is now v4, content=Y. 
           No version predicate to fail, UPDATE proceeds → v5, content=Z.
T2 audit: content_before=X (from stale snapshot!), content_after=Z.
                       ^^^ wrong — actual prior content was Y, not X
```

That's an audit log that lies about what changed. Bad for "full audit history."

Sharp question, but I want to push back on the framing a bit: the locking is already happening — `FOR UPDATE` doesn't *add* contention, it just relocates the wait.

### The lock is happening either way

In PostgreSQL READ COMMITTED, **any UPDATE takes a tuple-level exclusive lock** on the row it modifies, held until commit. So even without `FOR UPDATE` in `prior`:

```
Without FOR UPDATE in prior:
  T1: prior SELECT (snapshot, no lock) → UPDATE (takes lock) ... lock held ... COMMIT
  T2: prior SELECT (succeeds, stale)   → UPDATE (blocks on T1's lock) ... waits ... runs

With FOR UPDATE in prior:
  T1: prior SELECT (takes lock)        → UPDATE (already locked) ... lock held ... COMMIT  
  T2: prior SELECT (blocks on T1's lock) ... waits ... acquires lock at post-T1 state → UPDATE
```

T2 waits the same duration in both cases — the wait is dictated by T1's commit time, not by which CTE acquires the lock. `FOR UPDATE` doesn't introduce new pessimism; it just makes the read happen *after* the lock is held so the audit row sees the correct prior state.

### The actual cost of "no FOR UPDATE"

Not "more throughput" — it's "audit rows that lie." T2 reads stale `content_before` from its snapshot, then T2's UPDATE overwrites the post-T1 state, then T2's audit row records a `content_before` that nobody ever saw. The collaboration feature's whole point is "full audit history" — silently corrupted history is worse than a few microseconds of wait time.

### Scope of contention

Lock is per-`(report_id, section_key)` row. So what's blocked:

- ✅ **Two writes (PATCH or revert) to the same section** — serialize. This already happens today on PATCH.
- ❌ Writes to different sections of the same report — unaffected.
- ❌ Writes to other reports — unaffected.
- ❌ Reads (GET section / history / report) — `FOR UPDATE` doesn't block `SELECT`s. They proceed against the snapshot.
- ❌ Shares CRUD — different table.

The "concurrent reverts to the same section" workflow is genuinely rare — two users simultaneously hitting revert on the same key, within milliseconds. Even in heavy collaborative use, one revert + one PATCH on the same section is the worst case, and that already serializes today via PATCH's own lock.

### How this compares to PATCH

PATCH today: pessimistic lock (implicit via UPDATE) + optimistic version predicate. The predicate's job is **fail-fast** — instead of T2 silently waiting and overwriting, T2 gets 412 immediately and the client decides what to do.

Revert without If-Match: pessimistic lock (same as PATCH) + no fail-fast → last-write-wins. T2 waits, then wins. The lock isn't the new thing — losing fail-fast is.

So the real tradeoff isn't "pessimistic vs optimistic." It's "client gets told about conflicts (412)" vs "client doesn't know, last revert wins." That's the spec's call, and you already made it.

### Verdict

Acceptable, and arguably the cheapest correct option:

- Throughput unchanged from today's PATCH (same lock mechanism, same row scope).
- Audit log stays truthful under the race.
- Cost is one SQL keyword.

The only real alternative that avoids the lock is "accept corrupted audit rows," which I wouldn't recommend.

Proceed with `FOR UPDATE`?

### Service flow with the transaction-boundary rule in mind

```
1. require_edit_access dep             # reads, auto-tx
2. service: get_section                # read, same auto-tx
3. service: pre-check section.version  # see note below
4. await db.commit()                   # RELEASE the read tx ← critical
5. await llm_client.call(...)          # no DB resources held

7. interpret result → 412 or success
8. await db.commit()
9. log + return
```

**Step 4 is the key thing.** If we don't commit the read transaction before the LLM call, we hold an idle-in-transaction for the duration of the LLM call (seconds with a real provider). The pre-check at step 3 just short-circuits obviously stale requests *before* the LLM call so we don't burn tokens on a write that's guaranteed to 412. The rule's intent is to prevent the read-check-write anti-pattern where app code is the only safety; here, app code is an optimization and the predicate is still the safety.
